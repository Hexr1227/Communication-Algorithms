# 第七课：正常、突发与恢复业务

## 课前回顾

第六课已通过代码和聊天理解验收。四种算法共用队列推进器，每场使用同一业务/信道轨迹；一次C调用执行整场仿真。回顾：新包为何不能在到达当步发送？为何更换策略时要重置队列与PF历史？

## 本课所需知识

Bernoulli（伯努利）到达表示每次只有“到达/不来”两种结果。每用户每时隙以概率p到达一个包，大小固定为L个数据单位，因此预期到达量为p*L单位/用户/时隙。U位用户的预期总到达量为U*p*L，不是实际每个时隙都恰好有这么多。

本课依次生成正常、突发、恢复三段，恢复段使用正常概率。这是一种人为设定的非平稳业务模型，不是来自真实演唱会数据的校准模型。可以用恢复概率0观察队列清空；当正常到达仍不为0时，恢复并不保证清空。p变大也不自动证明系统过载，必须结合共享资源容量判断。

random.Random(seed)提供独立的局部伪随机数源；其random()产生[0,1)内的数。你需自己把该数与概率联系起来，得到0或packet_size。固定种子可重现轨迹，不应在每个时隙重新设种子。生成一次输入并由四种策略共享，不要每个算法各重新抽一次。不同种子不是数学上必然产生不同轨迹，特别是概率0/1或极短序列。

函数关键字参数由*限定，调用时要明确写users=...等名称。矩阵每行应是独立列表，避免修改一行时其他行跟着变。细节契约见student.py，概率0/1也按同一抽样顺序消耗随机数，便于测试与复现。

## 手算作业

U=4、L=2，正常概率0.1、突发概率0.8，分别计算每时隙预期总到达量。假设每个被选用户的容量都是2，每时隙最多服务一位用户，系统最多发多少？哪个阶段可能持续积压？注意低于该上限并不能单独证明每个用户队列稳定。

再设正常2时隙、突发3时隙、恢复2时隙，U=2、L=3、normal_p=0、burst_p=1。请手写完整到达矩阵，不需要随机计算。
